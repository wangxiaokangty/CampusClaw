## Context

动机见 [proposal.md](proposal.md)。当前 `backend/app/config.py` 根据文件路径生成 SQLite 地址；`app/db.py` 创建数据目录、设置线程参数和 SQLite PRAGMA。`app/main.py` 启动时建表、按 `Class` 是否为空装载种子，再恢复滞留批改。

`models/tables.py` 有 14 张业务表，使用字符串主键、外键、枚举、布尔值、无时区日期及 JSON 列。`utcnow()` 实际调用 `datetime.now()`；本次不顺带修改其时间语义。后台批改经 `new_session()` 获取独立会话。现有测试使用内存 SQLite 与 StaticPool，并替换模块级引擎。

Compose 当前挂载 SQLite 数据卷，前端通过 `http://backend:8000` 代理 `/api`，对外端口为 3000。没有已登记的主规格，已完成但未归档的 `bootstrap-api-skeleton` 保留业务规格及旧 SQLite 决策。此提案只取代数据库相关决策，不修改其历史文件和既有业务要求。

## Goals / Non-Goals

**Goals:**
- 通过连接、驱动、必要的存储兼容和部署改动实现 PostgreSQL 单一运行后端。
- 以原有测试、迁移前后数据对照及接口契约对照证明行为兼容。
- 支持新库初始化和已有 SQLite 数据迁移两个独立入口，避免自动种子抢先污染迁移目标。

**Non-Goals:**
- 不改变页面、认证、业务状态机、模拟人工智能内容及模型与响应结构分离方式。
- 不引入异步 ORM（Object-Relational Mapping，对象关系映射）、任务队列、连接代理或高可用架构。
- 不引入 Alembic 等通用版本迁移框架，不进行业务表重设计或时间格式规范化。
- 不提供长期双库运行、自动双写或在线无停机搬迁。

## Decisions

### D1：保留同步 SQLModel，使用 Psycopg 3

增加 `psycopg[binary]` 并更新 uv 锁文件，使用 `postgresql+psycopg://` 连接。`Settings` 增加数据库地址配置，移除旧文件路径的运行用途；允许将标准 `postgresql://` 地址规范化为选定驱动形式。启动时检查配置并连接验证，缺失或非 PostgreSQL 配置明确失败，日志屏蔽凭据。OpenAPI 导出不应触发实际数据库连接，可在导出检查时提供无需可达的合法占位连接地址。

删除数据目录创建、`check_same_thread` 和 PRAGMA，保留 `get_session()`、`new_session()` 及现有同步会话边界。可开启连接存活检查，避免重连后复用失效连接。没有需求支持运行期 SQLite，因此不保留双方言自动回退。异步驱动需要改动大量调用方，超出本次范围。

### D2：保持逻辑模型，显式防止类型及排序漂移

继续使用 `metadata.create_all()` 初始化空目标库并调用原有 seed；完整迁入后 `Class` 非空，正常启动跳过 seed。迁移工具在启动应用前独立运行，不调用 lifespan。

保留 JSON 列而不顺带改成 JSONB，日期继续使用无时区语义，保留原有字符串主键、列名、索引、外键及级联关系。枚举建议显式使用非原生字符串存储，保持既有 SQLAlchemy 枚举编码及接口字符串；避免数据库原生枚举的排序与原字符串排序不同。实际数据库编码以源库和现有模型的读写结果核对，不直接把枚举名字当成接口值。

本地 PostgreSQL 初始化选择 UTF-8 编码与 `C` 排序规则；外部数据库也必须满足相同的可观察排序。针对 `auth.py` 的角色顺序、助手和作业的中文学科排序，以及服务中无显式排序但会影响模拟输出的候选数据，记录 SQLite 基线并对照 PostgreSQL。如果环境默认排序不同，在相关查询或存储列上显式指定兼容排序，调整仅用于还原原有表现。原本未定义的并列顺序不新增业务规则，但影响展示或评分结果时必须用基线覆盖。

### D3：部署增加数据库服务，应用入口保持

Compose 使用固定主版本的 PostgreSQL 镜像（计划采用 `postgres:17`，实施时锁定并验证具体镜像），配置 `pg_isready` 健康检查和独立持久化卷；后端依赖数据库健康后启动。开发环境按文档设置数据库用户名、密码、库名和连接地址，凭据通过环境配置，不提交真实密码。

前端构建参数、服务名、3000 端口、代理及后端 `/health` 响应不变。后端 Dockerfile 去掉 SQLite 的环境变量和 `/data` 卷声明；原 SQLite 卷保留用于迁移和回退，不自动删除。数据库默认仅在 Compose 内网提供服务；宿主机开发和测试的本地端口通过明确的开发配置开放。

### D4：一次性迁移采用只读源快照、空目标和完整事务

新增 `backend/scripts/migrate_sqlite_to_postgresql.py`，显式接收 SQLite 快照路径和通过环境提供的目标地址。用 SQLAlchemy 表元数据按外键拓扑读取及写入全部 14 张表；不调用重新生成标识或默认时间的业务创建函数。源库以只读方式打开，任何表的现有目标数据都导致拒绝。工具检查源表结构与当前模型匹配，发现缺列、未知业务表、非法枚举或孤立引用时明确失败，不静默跳过。

建表可以先行；全部业务写入和校验放在同一个目标事务中。通过类型处理保留 JSON、空值、布尔值、日期和枚举含义，按主键逐表对比数量、主键集合和规范化后的全部字段；JSON 对象键顺序可规范化，数组顺序不得改变。校验失败回滚本次业务记录，允许留下空表结构。报告仅输出表名、数量、失败字段或记录标识，不输出学生正文、助手密钥和数据库密码。

选择拒绝非空目标而非 upsert，避免重试覆盖真实数据；失败后可向同一空目标重试，成功后再次执行必须拒绝。迁移期间源和目标均不得被应用写入。SQLite 快照通过数据库备份机制制作，不能在有写入或 WAL（Write-Ahead Logging，预写日志）尚未合并时仅复制主文件。保留源快照和旧发布版本作为回退依据。

### D5：全量测试在真实 PostgreSQL 上隔离运行

使用专用 `CAMPUSCLAW_TEST_DATABASE_URL` 和测试数据库，不对生产连接执行清理。每个测试建立随机命名 schema（模式）并设置所有连接的搜索路径，让请求、lifespan 和后台任务共享同一测试 schema；测试结束释放会话及连接后仅删除该 schema。测试数据库角色需要建删 schema 权限，测试地址在导入应用前配置好。

保留现有认证、讲义、助手、对话、批改、错题、审计、关怀、学情和跨班断言，替换 SQLite 专用夹具；验证 lifespan 使用的引擎也被正确替换。不能仅依赖请求会话外层事务回滚隔离测试，因为后台任务会建立连接并自行提交。保留 SQLite 仅作为迁移工具的源输入与迁移测试夹具。

增加真实启动与重启测试、连接失败测试、迁移完整性及失败回滚测试。实施前保存 OpenAPI 基线，实施后对照，并执行现有 `npm run check:api`。业务断言不能因 PostgreSQL 的差异被放宽；差异必须在存储兼容层解决。

## Risks / Trade-offs

- 数据类型严格性和外键约束暴露历史异常 → 迁移预检、逐字段校验、全事务回滚；不擅自修复或删除数据。
- 排序规则、枚举存储及无序查询改变输出 → 使用同一数据集记录 SQLite 基线并运行 PostgreSQL 对照，覆盖页面列表和模拟评分引用。
- 种子数据先于迁移写入 → 先仅启动 PostgreSQL 并执行迁移，验证后再启动后端。
- 多进程同时 seed 的竞态仍可能存在 → 保持当前部署进程模式；本次不增加副本或重构初始化机制。
- PostgreSQL 引入服务运行成本及测试依赖 → 提供可复现 Compose 启动和专用测试库说明，不退回内存 SQLite 作为验收依据。
- 切换后新增写入无法用旧快照直接回退而不丢失 → 恢复用户写入前完成验收；恢复写入后的故障以 PostgreSQL 修复或备份恢复处理，不承诺自动反向迁移。

## Migration Plan

1. 在当前版本记录接口、种子及关键展示/排序基线，完成实现和真实 PostgreSQL 回归。
2. 新安装：配置连接与凭据，启动 Compose，验证自动建表、seed 和原有页面流程。
3. 存量安装：停止后端及所有写入，保留旧版本与旧配置，制作并验证一致的 SQLite 备份；源库和旧卷不删除。
4. 仅启动空 PostgreSQL，运行独立迁移工具，核对全部表、字段及关联；失败则保持停写或恢复旧版本与源库，重试前确认目标为空。
5. 切换后端连接，保持原有认证密钥及其他非数据库设置，启动并验证登录、权限、对话、批改、审计、关怀和统计，再允许用户写入。滞留批改可能在启动时写入，验收阶段的此类写入应记录，以便回退时由旧库按原规则恢复任务。
6. 验证容器重建后的数据留存。若开放写入前失败，停止新后端，恢复旧版本、配置和 SQLite 快照；开放后不得直接以旧快照替代新库。
7. 更新 README、Markdown 迁移说明和 `openspec/config.yaml` 技术栈，保留旧提案的历史描述。实际线上数据库地址与维护窗口在部署时配置，本轮不访问或修改线上系统。
